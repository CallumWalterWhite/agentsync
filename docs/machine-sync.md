# Manual encrypted machine-to-machine sync

This first Phase 2 slice transfers immutable snapshots through a private relay. Machine A encrypts for machine B; machine B imports into its AgentSync catalog. It does not make an imported session resumable in Codex or Claude.

For a disposable browser demo without configuring real machine keys, use the [Docker showcase](../deploy/README.md).

## Install

Build from this repository on each client machine:

```sh
cargo install --path crates/agentsync-cli --locked --force
```

On the relay host:

```sh
cargo install --path crates/agentsync-server --locked --force
```

The implementation targets macOS/Linux. For this milestone the relay uses a private disk directory; PostgreSQL and S3 are not required.

## Relay access

Generate one access token in a trusted secret manager, or with `openssl rand -hex 32`. Supply the same value to the relay host and both clients through `AGENTSYNC_RELAY_TOKEN`. Keep it out of command arguments, shell history and logs. The application reads the environment only and does not save it.

Start the relay with an absolute path to a **new** directory whose parent already exists:

```sh
agentsync-server --data-dir /absolute/private/agentsync-relay
```

It listens on `127.0.0.1:8787`. Existing directories must already be AgentSync relay directories with mode 0700. One process can own a relay directory at a time.

Expose the loopback listener through an HTTPS reverse proxy, for example at `https://sync.example.com`. Allow request bodies up to 272 MiB and transfer durations of at least 120 seconds. Keep upstream response compression disabled; the bytes are already encrypted. Avoid logging Authorization headers, bodies or secrets. The clients require a valid HTTPS certificate and do not follow redirects or environment proxy settings.

For a private first test, an SSH tunnel also works. On each client, keep a separate terminal running:

```sh
ssh -N -L 8787:127.0.0.1:8787 user@relay-host
```

Use `http://127.0.0.1:8787` as the server origin through that tunnel. The application itself never reads SSH keys or invokes SSH.

## Recipient keys

Use an X25519 identity generated by standard [age tooling](https://github.com/FiloSottile/age#usage), such as `age-keygen` or `rage-keygen`. Generate and retain the key on machine B using that tool or your secret-management workflow. Never commit it to this repository.

- Give machine A only B's public recipient (`age1...`) through a trusted channel.
- Supply B's secret identity (`AGE-SECRET-KEY-...`) as `AGENTSYNC_AGE_IDENTITY` when running pull. This must be the single identity value, without a key file's comment lines.
- AgentSync does not generate, read key files, save, recover or transmit that private identity.
- The relay receives neither the private identity nor the public recipient; age headers can still reveal the encryption format and recipient count.

For reverse transfers, generate/use A's own recipient and identity. This milestone encrypts each transfer for one recipient.

## Push from machine A

Use an existing snapshot ID (`snp_...`), not a session ID (`ags_...`):

```sh
agentsync discover
agentsync snapshot ags_YOUR_SESSION_ID
agentsync push snp_YOUR_SNAPSHOT_ID \
  --server https://sync.example.com \
  --recipient age1_RECIPIENT_FROM_MACHINE_B
```

`AGENTSYNC_RELAY_TOKEN` must be set. Push validates the complete bundle, encrypts its manifest/receipt/objects, uploads it, and prints a transfer SHA-256. Send that hash to B through a trusted channel. The hash identifies the exact encrypted bytes; it is not the manifest hash or snapshot ID.

## Pull on machine B

With `AGENTSYNC_RELAY_TOKEN` and `AGENTSYNC_AGE_IDENTITY` set:

```sh
agentsync pull TRANSFER_SHA256_FROM_A --server https://sync.example.com
agentsync bundle list
agentsync bundle verify snp_IMPORTED_SNAPSHOT_ID
```

Pull verifies the pinned ciphertext hash, decrypts, screens every archive entry, validates the existing bundle format and registers a complete immutable import. Repeating the same pull succeeds without creating another import. Both commands support the existing `--json` option.

Local session discovery and provider files remain unchanged. `agentsync sessions` lists local provider sessions; `agentsync bundle list` lists received snapshots.

## Limits and troubleshooting

- One relay serves one shared trust group. There are no separate accounts or per-device access permissions.
- Maximum encrypted transfer: 272 MiB. Total relay storage: 1 GiB. Native object/bundle limits remain 128/256 MiB. Buffers can require several times the transfer size in RAM.
- `401`: missing or wrong relay token. `404`: unknown transfer hash. `409`: an existing relay object failed verification or publication conflicted. `413`: body too large. `503`: relay busy; retry later. `507`: quota exhausted.
- A failed key check means the transfer was not encrypted for the supplied identity, or its envelope is invalid. No import is registered.
- Sensitive-content refusals stay strict during exchange. `snapshot --force` only changes local capture; it does not make keyword-blocked bundles transferable.
- Retransmitting identical encrypted bytes is idempotent. Running push again creates fresh randomized ciphertext and therefore another relay object.
- There is no automatic sync, remote listing, upload resumption, deletion or cleanup. Retained staging data counts toward quota. Keep the directory for inspection after interrupted writes.
- Tests use two temporary stores and real loopback HTTP. Public HTTPS hosting and separate physical machines still need deployment validation.

See [ADR 0008](ADR/0008-encrypted-relay-basics.md) for boundaries and wire behavior.
